                         ABSTRACT
================================================================================

In the modern educational ecosystem, the administrative processes related to
student certificate requests and leave applications remain predominantly
paper-based, leading to inefficiencies, delays, and loss of documents. The
College Certificate and Request Management System (SEC Flow) addresses this
challenge by providing a comprehensive digital platform that automates the
entire workflow of certificate issuance and request approval in an academic
institution.

This project presents a full-stack web and mobile application built using
React Native with Expo framework for the frontend client and Python Flask
for the backend RESTful API server. The system supports four distinct user
roles: Students, Staff members, Heads of Department (HOD), and System
Administrators. It manages three types of requests: Leave Applications,
Bonafide Certificate Requests, and Gatepass Permissions, each following a
two-tier approval workflow where requests progress from staff-level review
to HOD-level final approval.

The system employs JWT (JSON Web Token) based authentication for secure
access control, MySQL as the primary relational database with SQLite
fallback support, and implements role-based access control (RBAC) to ensure
that users can only access data and functionality relevant to their
designated roles. The application generates professional PDF certificates
using HTML-to-PDF conversion, enabling students to download and share
approved documents digitally.

The key contributions of this project include: (1) elimination of paper-based
workflows, (2) reduction in processing time from days to minutes, (3)
transparent tracking of request status, (4) automated certificate generation,
and (5) centralized administrative control over user management. The system
demonstrates how modern cross-platform mobile development frameworks and
lightweight web servers can be combined to create practical solutions for
real-world institutional challenges.

Keywords: Certificate Management, Request Workflow, React Native, Flask,
JWT Authentication, Role-Based Access Control, PDF Generation, Cross-Platform
Mobile Application, Academic Administration, Digital Transformation.

1.1 OVERVIEW

In the contemporary educational landscape, colleges and universities handle
numerous administrative tasks on a daily basis. Among these, the processing
of student requests for certificates, leave applications, and gatepass
permissions constitutes a significant portion of the administrative workload.
Traditionally, these processes have been managed through paper-based systems
where students fill out physical forms, submit them to the concerned
departments, and wait for manual approval through multiple levels of
authority.

The College Certificate and Request Management System, internally referred
to as "SEC Flow" (Sengunthar Engineering College Flow), is designed to
digitize and streamline these administrative processes. The system provides
a unified digital platform where students can submit various types of
requests, staff and HODs can review and approve them, and administrators
can manage the entire user ecosystem.

The project leverages modern software development paradigms to deliver a
cross-platform mobile application that works seamlessly on Android, iOS,
and web browsers. The frontend is developed using React Native with the
Expo managed workflow, which allows for rapid development and deployment
across multiple platforms from a single codebase. The backend is built
using Python Flask, a lightweight and flexible web framework that provides
RESTful API services to the mobile client.

The system addresses a real-world problem faced by educational institutions:
the inefficiency of paper-based certificate and request management. By
digitizing this process, the system reduces processing time, eliminates
paper waste, provides transparency in request tracking, and enables
students to download approved certificates instantly as PDF documents.

1.2 PROBLEM STATEMENT

The existing paper-based system for certificate and request management in
colleges suffers from several critical limitations:

1. Time-Consuming Process: Students must physically visit multiple offices
   to submit forms, obtain signatures, and collect certificates. A single
   bonafide certificate request may take 3-5 working days to process
   through the traditional workflow.

2. Document Loss: Paper forms and certificates are susceptible to being
   lost, damaged, or misplaced during the multi-level approval process.
   There is no reliable tracking mechanism to determine the current status
   of a submitted request.

3. Lack of Transparency: Students have no visibility into the approval
   process once a form is submitted. They cannot determine which level
   of authority is currently processing their request or what the reason
   for rejection might be.

4. Administrative Burden: Staff members and HODs spend considerable time
   manually reviewing, signing, and routing physical documents. This
   administrative overhead reduces the time available for academic
   activities.

5. No Historical Records: Paper-based systems do not maintain organized
   historical records of requests. Retrieving information about past
   requests or generating reports is nearly impossible.

6. Redundant Data Entry: Students often need to fill out the same personal
   information (name, roll number, department) on every form they submit,
   leading to redundant data entry and potential inconsistencies.

7. Physical Presence Requirement: Students must be physically present on
   campus to submit and collect documents, which is inconvenient for
   students who are off-campus due to internships, medical reasons, or
   other circumstances.

8. Environmental Impact: The paper-based system consumes significant
   amounts of paper, contributing to environmental degradation and
   unnecessary institutional expenses.

The proposed system aims to address all these limitations by providing a
comprehensive digital alternative that maintains the existing approval
hierarchy while eliminating the inefficiencies of the paper-based workflow.

1.3 OBJECTIVES

The primary objectives of the College Certificate and Request Management
System are as follows:

Primary Objectives:

2. To implement a two-tier approval workflow that mirrors the existing

3. To provide real-time tracking of request status, allowing students to
   monitor the progress of their submissions at every stage of the

4. To automate the generation of professional PDF certificates upon
   final approval, enabling students to download and share documents
   digitally without visiting the college office.

5. To establish role-based access control that ensures each user category
   (Student, Staff, HOD, Admin) can only access functionality and data
   appropriate to their role.

Secondary Objectives:

6. To create an administrative dashboard that allows system administrators
   to manage users, create staff and HOD accounts, and monitor system
   activity across all departments.

7. To implement secure authentication using JWT tokens, ensuring that
   only authorized users can access the system and that each user's
   data remains protected.

8. To design a responsive and intuitive user interface that requires
   minimal training and is accessible to users with varying levels of
   technical proficiency.

9. To support multiple departments within the institution, with
   department-based data isolation ensuring that staff and HODs can
   only access requests from their respective departments.

10. To provide offline resilience through local data caching, ensuring
    that the application remains functional even with intermittent
    network connectivity.

2.1 EXISTING SYSTEMS

2.1.1 Traditional Paper-Based System

The traditional system for certificate and request management in most
educational institutions operates entirely on paper-based workflows. In
this system, a student who requires a bonafide certificate must follow
these steps:

Step 1: Obtain the appropriate form from the college office or department
office. These forms are typically pre-printed and require manual filling.

Step 2: Fill out the form with personal details including name, roll
number, department, year of study, and the purpose for which the
certificate is required.

Step 3: Submit the completed form to the concerned staff member or class
advisor for initial verification and signature.

Step 4: After staff approval, the form is forwarded to the Head of
Department for final approval and signature.

Step 5: Once approved by the HOD, the form is submitted to the college
office where the certificate is manually typed or written.

Step 6: The student must return to the college office after 2-5 working
days to collect the printed certificate.

This process has several inherent problems:

- Physical presence is required at multiple stages
- Forms can be lost between departments
- No tracking mechanism exists
- Processing time is unpredictable
- Paper waste is generated at every step
- Historical records are difficult to maintain
- No backup exists if documents are damaged

2.1.2 Manual Digital Systems

Some institutions have attempted to digitize parts of this process using
basic digital tools:

Email-Based Systems: Some colleges accept requests via email. Students
send their details to a designated email address, and the administrative
staff processes the request manually. This approach has limitations:
- No structured workflow
- Email can be missed or overlooked
- No automated tracking
- Difficult to manage high volumes
- No integration with approval hierarchy

Google Forms Based Systems: Some institutions use Google Forms to collect
request data. While this captures data digitally, the approval workflow
remains manual and offline. Limitations include:
- No role-based access
- No approval workflow
- No certificate generation
- Data scattered across spreadsheets

Standalone Desktop Applications: Some colleges have developed desktop
applications for specific departments. These are typically limited to
a single department and do not support multi-user access or mobile
functionality.

2.1.3 Commercial ERP Systems

Large educational institutions often use Enterprise Resource Planning
(ERP) systems such as:

- SAP Education Management
- Oracle PeopleSoft Campus Solutions
- Ellucian Banner
- Jenzabar EX

These systems offer comprehensive management capabilities including
student information systems, financial management, and certificate
management. However, they have significant drawbacks for small to
medium-sized institutions:

- Extremely high licensing and implementation costs
- Complex setup requiring IT specialists
- Overwhelming feature set for simple certificate management
- Long implementation timelines (6-18 months)
- Vendor lock-in and dependency
- Requires dedicated server infrastructure

2.2 RELATED WORK

2.2.1 Academic Research

Several researchers have addressed the problem of academic administrative
automation:

Kumar and Singh (2019) proposed a web-based certificate management
system using PHP and MySQL. Their system supported online form submission
and certificate generation but lacked mobile support and a multi-level
approval workflow.

Patel et al. (2020) developed an Android application for leave management
in educational institutions. The application supported leave application
submission and approval but was limited to leave requests only and did
not include certificate management.

Zhang and Liu (2021) implemented a blockchain-based certificate verification
system. While innovative, their approach focused on certificate verification
rather than the request and approval workflow, and the blockchain
infrastructure added unnecessary complexity for institutional use.

Sharma et al. (2022) developed a cloud-based student service portal using
React and Node.js. Their system included certificate requests but used a
single-tier approval process and lacked department-based data isolation.

2.2.2 Industry Solutions

Several commercial solutions exist in the market:

Fedena: An open-source school management system that includes some
certificate management features. However, it is designed primarily for
K-12 education and lacks the complex approval workflows needed for
higher education institutions.

MasterSoft: A comprehensive ERP solution for Indian educational
institutions. While it includes certificate management, it is a paid
solution with costs that may be prohibitive for smaller institutions.

Catalyst: A student information system that offers certificate generation.
However, it requires cloud subscription fees and does not support offline
functionality.

2.2.3 Gap Analysis

The literature survey reveals several gaps in existing solutions:

1. Most systems focus on either leave management OR certificate
   management, but not both in an integrated platform.

2. Existing solutions typically use single-tier approval workflows,
   whereas academic institutions require multi-tier approval
   (Staff -> HOD -> Principal).

3. Mobile-first solutions are rare; most systems are web-only,
   which is limiting for students who primarily use smartphones.

4. Affordable solutions that combine simplicity with comprehensive
   feature sets are scarce in the market.

5. Department-based data isolation is often missing in existing
   systems, leading to privacy concerns.

2.3 TECHNOLOGY OVERVIEW

2.3.1 React Native

React Native is an open-source mobile application framework developed by
Facebook (now Meta) in 2015. It allows developers to build native mobile
applications using JavaScript and React, a popular web UI library.

Key Features:

- Cross-Platform Development: React Native enables developers to write
  code once and deploy it on both Android and iOS platforms. This
  significantly reduces development time and cost compared to building
  separate native applications for each platform.

- Native Components: Unlike hybrid frameworks that use WebView to render
  HTML content, React Native uses actual native UI components. This means
  a React Native app looks and feels like a truly native application.

- Hot Reloading: React Native supports hot reloading, which allows
  developers to see changes in real-time without rebuilding the entire
  application. This dramatically speeds up the development process.

- Large Ecosystem: React Native has a vast ecosystem of third-party
  libraries and components, making it easy to add functionality such as
  navigation, animations, and device API access.

Architecture:

React Native uses a bridge architecture to communicate between the
JavaScript code and the native platform. The JavaScript code runs in a
separate thread (JS thread), and communication with native modules
occurs through a serialized message bridge. In newer versions, the
New Architecture with Fabric renderer and JSI (JavaScript Interface)
provides direct communication without the bridge, improving performance.

Why React Native for this Project:

1. The target users (students) primarily use mobile devices
2. Cross-platform support reduces development effort
3. Large community and extensive documentation
4. Expo managed workflow simplifies builds and deployment
5. Hot reloading enables rapid development

2.3.2 Expo Framework

Expo is a framework and platform built around React Native that provides
a managed workflow for developing, building, and deploying React Native
applications.

Key Features:

- Managed Workflow: Expo handles the complex native build configuration,
  allowing developers to focus on JavaScript code without worrying about
  Android Studio or Xcode configurations.

- Expo SDK: A comprehensive set of pre-built libraries that provide
  access to native device APIs such as camera, file system, location,
  and more, all accessible from JavaScript.

- Over-The-Air Updates: Expo allows developers to push JavaScript updates
  directly to users without going through app store review processes.

- Expo Go: A companion app that allows developers to test their
  applications on physical devices without building native binaries.

- EAS (Expo Application Services): A cloud-based build service that
  compiles and distributes applications to app stores.

Why Expo for this Project:

1. Simplified development workflow
2. Built-in support for PDF generation (expo-print)
3. Built-in file sharing (expo-sharing)
4. Easy deployment to app stores
5. Managed updates for bug fixes

2.3.3 Python Flask

Flask is a lightweight web application framework written in Python. It
was created by Armin Ronacher in 2010 and is classified as a micro-
framework because it does not require particular tools or libraries.

Key Features:

- Lightweight: Flask has a small footprint and minimal dependencies,
  making it fast and easy to deploy.

- Flexible: Unlike full-stack frameworks like Django, Flask does not
  enforce a particular project structure or database ORM, giving
  developers complete freedom in architecture decisions.

- Extensible: Flask supports extensions that add functionality such as
  database integration, form validation, and authentication.

- RESTful: Flask is well-suited for building RESTful APIs due to its
  simple routing and request/response handling.

- WSGI Compliant: Flask follows the Web Server Gateway Interface (WSGI)
  standard, ensuring compatibility with various web servers.

Architecture:

Flask follows the Model-View-Controller (MVC) pattern, though it does
not enforce it strictly. In this project:

- Models: SQLAlchemy ORM classes define database tables
- Views: Route handlers (decorated functions) process requests
- Controller: Business logic within route handlers

Why Flask for this Project:

1. Simple and easy to learn
2. Quick prototyping capabilities
3. Excellent SQLAlchemy integration
4. Built-in development server
5. Suitable for lightweight API services

2.3.4 MySQL Database

MySQL is an open-source relational database management system (RDBMS)
based on Structured Query Language (SQL). It is one of the most widely
used database systems in the world.

Key Features:

- Relational Model: MySQL stores data in tables with rows and columns,
  supporting relationships between tables through foreign keys.

- ACID Compliance: MySQL supports Atomicity, Consistency, Isolation,
  and Durability properties, ensuring reliable transaction processing.

- Scalability: MySQL can handle large volumes of data and concurrent
  connections, making it suitable for production environments.

- Security: MySQL provides user authentication, access control, and
  encrypted connections.

- Replication: MySQL supports master-slave replication for high
  availability and read scaling.

Why MySQL for this Project:

1. Open-source and free to use
2. Widely supported and well-documented
3. Excellent Python integration through PyMySQL
4. Reliable and production-tested
5. Supports complex queries needed for reporting

2.3.5 JWT Authentication

JSON Web Token (JWT) is an open standard (RFC 7519) for securely
transmitting information between parties as a JSON object. It is widely
used for authentication in modern web and mobile applications.

How JWT Works:

1. User submits credentials (username and password) to the server.
2. Server validates credentials and generates a JWT containing user
   information and an expiration timestamp.
3. Server signs the JWT with a secret key using a cryptographic
   algorithm (typically HMAC-SHA256).
4. Server sends the JWT to the client.
5. Client stores the JWT and includes it in the Authorization header
   of subsequent requests.
6. Server verifies the JWT signature on each request to authenticate
   the user.

JWT Structure:

A JWT consists of three parts separated by dots:

Header: Contains the token type (JWT) and signing algorithm (HS256).
Payload: Contains claims (user data, expiration, etc.).
Signature: Created by encoding the header and payload with a secret key.

Why JWT for this Project:

1. Stateless authentication (no server-side session storage)
2. Cross-platform compatibility
3. Compact token size suitable for mobile storage
4. Built-in expiration for security
5. Easy to implement with PyJWT library

3.1 REQUIREMENT ANALYSIS

Requirement analysis is the process of determining user expectations for a
new or modified product. It involves identifying and documenting the
precise requirements that the system must satisfy. The requirements are
gathered through observation, interviews, and analysis of the existing
paper-based workflow.

3.1.1 Stakeholder Identification

The following stakeholders have been identified for this system:

1. Students: Primary users who submit requests and download certificates.
   They require an intuitive interface, quick submission process, and
   real-time status tracking.

2. Staff Members: Users who review and approve requests at the first level.
   They require efficient request listing, easy approval/rejection actions,
   and the ability to add remarks.

3. Heads of Department (HOD): Users who provide final approval for requests.
   They require visibility into staff-approved requests, comprehensive
   request details, and final decision-making capabilities.

4. Administrators: Users who manage the system, create user accounts, and
   oversee all departments. They require comprehensive dashboards, user
   management tools, and system maintenance utilities.

3.1.2 Existing Workflow Analysis

The current paper-based workflow was analyzed by observing the process
at Sengunthar Engineering College:

Current Workflow for Bonafide Certificate:
1. Student collects form from office (5 minutes travel time)
2. Student fills form manually (10-15 minutes)
3. Student submits to staff member (waiting time: 0-30 minutes)
4. Staff reviews and signs (1-2 days processing)
5. Form forwarded to HOD (1 day transit)
6. HOD reviews and signs (1-2 days processing)
7. Form sent to office for certificate typing (1 day)
8. Certificate printed (1 day)
9. Student notified to collect (travel time: 5-30 minutes)

Total Processing Time: 5-7 working days
Total Student Time Investment: 2-3 hours (including travel and waiting)

Proposed Digital Workflow:
1. Student opens app and fills form (2-3 minutes)
2. Staff receives notification and reviews (same day)
3. HOD receives notification and approves (same day)
4. PDF certificate generated automatically (instant)
5. Student downloads certificate (instant)

Total Processing Time: 1-2 working days
Total Student Time Investment: 5 minutes

This analysis demonstrates a potential time savings of 80-90% in both
processing time and student effort.

3.2 FUNCTIONAL REQUIREMENTS

Functional requirements define what the system should do. They describe
the specific behaviors, functions, and features that the system must
provide.

3.2.1 Authentication Module

FR-1: The system shall allow students to register themselves by providing
their roll number, name, department, gender, email, phone number, and
password.

FR-2: The system shall allow all user types (Student, Staff, HOD, Admin)
to authenticate using their unique identifier and password.

FR-3: The system shall generate a JWT token upon successful authentication
and return it to the client along with user role, name, gender, and
department information.

FR-4: The system shall validate the JWT token on every API request and
reject requests with missing, expired, or invalid tokens with a 401
Unauthorized response.

FR-5: The system shall store authentication tokens securely on the client
device using AsyncStorage for persistence across app restarts.

3.2.2 Student Module

FR-6: The system shall allow students to submit leave requests by providing
a title, leave type, start date, end date, and optional description.

FR-7: The system shall allow students to submit bonafide certificate
requests by providing a title, purpose, certificate type, and optional

4.1 SYSTEM ARCHITECTURE

The system follows a Client-Server Architecture, which is a distributed
application structure that partitions tasks or workloads between the
providers of a resource or service (servers) and the service requesters
(clients).

4.1.1 Architectural Pattern

The architecture is based on the REST (Representational State Transfer)
architectural style, which uses HTTP methods to perform CRUD (Create,
Read, Update, Delete) operations on resources. The key principles of
REST applied in this system are:

1. Client-Server Separation: The frontend (mobile app) and backend
   (API server) are completely separate, communicating only through
   HTTP requests and responses.

2. Stateless Communication: Each API request contains all the information
   needed to process it. The server does not store client state between
   requests (authentication is handled via JWT tokens).

3. Cacheable Responses: API responses can be cached by the client to
   improve performance and reduce server load.

4. Layered System: The architecture is organized into layers (presentation,
   business logic, data access), each with a specific responsibility.

4.1.2 Architectural Components

The system consists of the following architectural components:

Layer 1: Presentation Layer (Client)
- React Native mobile application
- Screen components for user interaction
- Reusable UI components (buttons, cards, inputs)
- State management through React Context API
- Local storage through AsyncStorage

Layer 2: Application Layer (Client)
- API service layer for HTTP communication
- Authentication service for login/logout
- Request services (leave, bonafide, gatepass)
- PDF generation service
- Theme management service

Layer 3: Network Layer
- HTTPS transport protocol
- JSON data format
- JWT authentication tokens
- Axios HTTP client library

Layer 4: Application Layer (Server)
- Flask web framework
- RESTful API endpoints
- JWT authentication middleware
- Role-based access control decorators
- Request validation and error handling

Layer 5: Data Access Layer (Server)
- SQLAlchemy ORM
- Database models (Student, Staff, Admin, Requests)
- Query execution and result mapping
- Transaction management

Layer 6: Data Layer
- MySQL database (primary)
- SQLite database (fallback)
- Six tables (students, staff, admins, leave_requests,
  bonafide_requests, gatepass_requests)

4.2 DATABASE DESIGN

Database design is the process of producing a detailed data model of the
database. This logical data model contains all the needed logical and
physical design choices and physical storage parameters.

4.2.1 Entity-Relationship Model

The database design is based on the Entity-Relationship (ER) model, which
represents data as entities (objects) and relationships (associations
between entities).

Entities Identified:

1. Student: Represents a registered student user
   Attributes: id, roll_no, name, gender, department, email, phone,
               reg_no, academic_year, password_hash, created_at

2. Staff: Represents a staff member or HOD user
   Attributes: id, staff_id, name, gender, department, email, phone,
               password_hash, role, general_info, created_at

3. Admin: Represents a system administrator
   Attributes: id, admin_id, name, password_hash, created_at

4. LeaveRequest: Represents a leave application
   Attributes: id, student_roll_no, student_name, department, title,
               description, leave_type, start_date, end_date, status,
               staff_remark, staff_id, hod_remark, hod_id, created_at,
               updated_at

5. BonafideRequest: Represents a bonafide certificate request
   Attributes: id, student_roll_no, student_name, department, title,
               description, purpose, certificate_type, status,
               staff_remark, staff_id, hod_remark, hod_id, created_at,
               updated_at

6. GatepassRequest: Represents a gatepass permission request
   Attributes: id, student_roll_no, student_name, department, title,
               description, reason, visit_place, visit_date, out_time,
               in_time, pass_id, status, staff_remark, staff_id,
               hod_remark, hod_id, created_at, updated_at

4.2.2 Relationships

The relationships between entities are as follows:

1. Student to LeaveRequest: One-to-Many
   A student can submit multiple leave requests.
   A leave request belongs to one student.

2. Student to BonafideRequest: One-to-Many
   A student can submit multiple bonafide requests.
   A bonafide request belongs to one student.

3. Student to GatepassRequest: One-to-Many
   A student can submit multiple gatepass requests.
   A gatepass request belongs to one student.

4. Staff to Requests: One-to-Many
   A staff member can approve/reject multiple requests.
   A request can be reviewed by one staff member.

5. HOD (Staff with role='hod') to Requests: One-to-Many
   An HOD can give final approval/rejection for multiple requests.
   A request can receive final decision from one HOD.

Note: While foreign key relationships exist logically, they are not
enforced at the database level in the current implementation. The
request tables store denormalized student data (student_name, department)
to avoid JOIN operations and maintain historical accuracy.

4.2.3 Normalization

The database design follows normalization principles to reduce data
redundancy and improve data integrity:

First Normal Form (1NF):
- All tables have atomic values (no repeating groups)
- Each column contains values of a single type
- Each column has a unique name
- The order of values does not matter

Second Normal Form (2NF):
- All tables are in 1NF
- No partial dependencies (all non-key attributes depend on the entire
  primary key)

Third Normal Form (3NF):
- All tables are in 2NF
- No transitive dependencies (non-key attributes do not depend on other
  non-key attributes)

Denormalization Note:
The request tables intentionally denormalize student_name and department
fields. This design decision trades some storage efficiency for:
- Faster query performance (no JOINs needed)
- Historical accuracy (request records reflect student data at the
  time of submission)
- Simplified query logic

4.4 WORKFLOW DESIGN

Workflow design defines the sequence of steps through which a request
progresses from submission to final disposition. The system implements
a two-tier approval workflow that mirrors the institutional hierarchy.

4.4.1 Workflow States

Each request exists in one of the following states:

State 1: PENDING
- Description: Request has been submitted by the student and is awaiting
  staff review.
- Transitions: Can transition to staff_approved or staff_rejected.
- Visible To: Student (own requests), Staff (department requests),
  Admin (all requests).

State 2: STAFF_APPROVED
- Description: Request has been approved by a staff member and is
  awaiting HOD final approval.
- Transitions: Can transition to hod_approved or hod_rejected.
- Visible To: Student (own requests), HOD (department requests),
  Admin (all requests).

State 3: STAFF_REJECTED
- Description: Request has been rejected by a staff member. This is
  a terminal state; the request cannot proceed further.
- Transitions: None (terminal state).
- Visible To: Student (own requests), Staff (department requests),
  Admin (all requests).

State 4: HOD_APPROVED
- Description: Request has received final approval from the HOD. The
  student can now download the certificate.
- Transitions: None (terminal state).
- Visible To: Student (own requests), HOD (department requests),
  Admin (all requests).

State 5: HOD_REJECTED
- Description: Request has been rejected by the HOD at the final level.
  This is a terminal state.
- Transitions: None (terminal state).
- Visible To: Student (own requests), HOD (department requests),
  Admin (all requests).

4.4.4 Department-Based Routing

The workflow incorporates department-based routing to ensure that
requests are reviewed by the appropriate authorities:

1. When a student submits a request, their department is recorded
   with the request.

2. Staff members can only see and act on requests from their own
   department.

3. HODs can only see and act on requests from their own department.

4. Administrators can see and act on requests from all departments.

This department-based isolation ensures privacy and proper delegation
of authority within the institution.

import React, { createContext, useContext, useState, useEffect } from 'react';
import AsyncStorage from '@react-native-async-storage/async-storage';

const AuthContext = createContext();

export const AuthProvider = ({ children }) => {
  const [user, setUser] = useState(null);
  const [loading, setLoading] = useState(true);

  // Check for existing session on app start
  useEffect(() => {
    checkAuthStatus();
  }, []);

  const checkAuthStatus = async () => {
    try {
      const token = await AsyncStorage.getItem('token');
      const role = await AsyncStorage.getItem('role');
      if (token && role) {
        setAuthToken(token);
        setUser({ token, role, /* ... */ });
      }
    } catch (error) {
      console.log('Storage check skipped');
    } finally {
      setLoading(false);
    }
  };

  const login = async (data) => {
    setAuthToken(data.token);
    await AsyncStorage.setItem('token', data.token);
    await AsyncStorage.setItem('role', data.role);
    setUser(data);
  };

  const logout = async () => {
    clearAuthToken();
    await AsyncStorage.clear();
    setUser(null);
  };

  return (
    <AuthContext.Provider value={{ user, login, logout, loading }}>
      {children}
    </AuthContext.Provider>
  );
};

5.3.2 Authentication Middleware

The token_required decorator validates JWT tokens on protected routes:

from functools import wraps
import datetime

def token_required(f):
    @wraps(f)
    def decorated(*args, **kwargs):
        token = None
        if 'Authorization' in request.headers:
            parts = request.headers['Authorization'].split()
            if len(parts) == 2 and parts[0] == 'Bearer':
                token = parts[1]

        if not token:
            return jsonify({'message': 'Token is missing!'}), 401

        try:
            data = jwt.decode(token, app.config['SECRET_KEY'],
                            algorithms=["HS256"])
            student = Student.query.filter_by(
                roll_no=data.get('roll_no')).first()
            staff = Staff.query.filter_by(
                staff_id=data.get('staff_id')).first()
            admin = Admin.query.filter_by(
                admin_id=data.get('admin_id')).first()
            current_user = student or staff or admin
            if not current_user:
                return jsonify({'message': 'User not found!'}), 401
        except Exception:
            return jsonify({'message': 'Token is invalid!'}), 401

        return f(current_user, *args, **kwargs)
    return decorated

5.3.3 Role-Based Access Control

The role_required decorator checks user roles before allowing access
to protected routes:

def role_required(*roles):
    def decorator(f):
        @wraps(f)
        def decorated_function(current_user, *args, **kwargs):
            user_role = None
            if isinstance(current_user, Student):
                user_role = 'student'
            elif isinstance(current_user, Staff):
                user_role = current_user.role
            elif isinstance(current_user, Admin):
                user_role = 'admin'

            if user_role not in roles:
                return jsonify({
                    'message': f'Access denied. Required: {roles}'
                }), 403
            return f(current_user, *args, **kwargs)
        return decorated_function
    return decorator

    if student and student.check_password(data['password']):
        token = jwt.encode({
            'roll_no': student.roll_no,

5.5 SECURITY IMPLEMENTATION

5.5.1 Password Hashing

Passwords are hashed using Werkzeug's generate_password_hash function,
which implements PBKDF2 (Password-Based Key Derivation Function 2) with
SHA-256:

from werkzeug.security import generate_password_hash, check_password_hash

class Student(db.Model):
    password_hash = db.Column(db.String(255), nullable=False)

    def set_password(self, password):
        self.password_hash = generate_password_hash(password)

    def check_password(self, password):
        return check_password_hash(self.password_hash, password)

The PBKDF2 algorithm works as follows:
1. Takes the plain-text password and a random salt
2. Applies SHA-256 hashing iteratively (default 260,000 iterations)
3. Stores the resulting hash along with the salt and algorithm info
4. During verification, the same process is applied and compared

5.5.2 JWT Token Security

JWT tokens are generated with the following security measures:

1. Secret Key: Tokens are signed with a server-side secret key that is
   never exposed to clients.

2. Expiration: Tokens expire after 7 days, limiting the window of
   vulnerability if a token is compromised.

3. Algorithm: HS256 (HMAC with SHA-256) is used for signing, providing
   strong cryptographic security.

4. Payload: Tokens contain only the minimum necessary information
   (user identifier and expiration), reducing the impact of token
   interception.

Token Generation:
token = jwt.encode({
    'roll_no': student.roll_no,
    'exp': datetime.datetime.utcnow() + datetime.timedelta(days=7)
}, app.config['SECRET_KEY'], algorithm="HS256")

Token Verification:
data = jwt.decode(token, app.config['SECRET_KEY'], algorithms=["HS256"])

5.5.3 Role-Based Access Control

The system implements RBAC through decorators that check user roles
before allowing access to protected resources:

- @token_required: Verifies the user is authenticated
- @role_required('student'): Restricts access to students only
- @role_required('staff', 'admin'): Restricts access to staff and admin

Department-based isolation adds an additional layer of access control:

6.1 TESTING METHODOLOGY

Testing is a critical phase of software development that ensures the
system meets its requirements and functions correctly. The testing
methodology followed for this project includes multiple levels of
testing:

6.1.1 Testing Levels

Level 1: Unit Testing
Individual components and functions are tested in isolation to verify
that each unit performs as designed. Unit tests focus on the smallest
testable parts of the application.

Level 2: Integration Testing
Multiple units are combined and tested together to verify that they
work correctly as a group. Integration tests focus on the interfaces
between components.

Level 3: System Testing
The complete system is tested as a whole to verify that it meets all
specified requirements. System tests are performed in an environment
that closely simulates production.

Level 4: User Acceptance Testing
End users test the system to verify that it meets their needs and is
ready for deployment. UAT focuses on real-world usage scenarios.

6.1.2 Testing Approach

The testing approach follows these principles:

1. Test Early, Test Often: Testing is performed throughout the
   development process, not just at the end.

2. Test Independence: Tests are designed to be independent of each
   other, so the failure of one test does not affect others.

3. Test Completeness: All requirements are tested, including both
   positive and negative scenarios.

4. Test Documentation: All test cases, procedures, and results are
   documented for traceability.

7.1 SYSTEM SCREENSHOTS

The following screenshots demonstrate the key screens of the application:

7.1.1 Login Screen
The login screen provides a unified entry point for all user types. Users
enter their identifier (roll number, staff ID, or admin ID) and password.
Links to signup and staff login are provided for easy navigation. The
screen features the institutional logo and branding in the header.

7.1.2 Student Registration Screen
The registration screen collects student information including roll number,
name, gender, department, email, phone number, and password. Department
selection is provided through a dropdown picker. Password confirmation
ensures accurate password entry.

7.1.3 Student Dashboard
The student dashboard serves as the central hub for all student activities.
It displays three primary action cards for Leave, Bonafide, and Gatepass
requests. The dashboard also shows the student's profile information
including name, roll number, and department. Quick access to request
status tracking is provided.

7.1.4 Leave Request Form
The leave request form collects information about the leave application
including title, leave type, start date, end date, and an optional
description. The form uses platform-native date pickers for accurate
date selection. Validation ensures all required fields are completed
before submission.

7.1.5 Bonafide Request Form
The bonafide request form collects information about the certificate
request including title, purpose (from predefined options), certificate
type (Bonafide, Character, or Income), and an optional description.
The purpose picker provides common use cases for quick selection.

7.1.6 Gatepass Request Form
The gatepass request form collects information about the gatepass
permission including title, reason, visit place, visit date, and out
time. The form generates a unique pass ID automatically upon submission.

7.1.7 Request Status Screen
The status screen displays all submitted requests in a list format. Each
request item shows the title, date, and a color-coded status badge
(Pending in amber, Approved in green, Rejected in red). Users can tap
on any request to view detailed information.

7.1.8 Request Detail Screen
The detail screen provides comprehensive information about a specific
request including all submitted fields, approval remarks from staff and
HOD, and the complete approval history. This screen enables students to
understand exactly where their request stands in the workflow.

7.1.9 Certificate Screen
The certificate screen displays a preview of the generated certificate
with institutional branding, student details, and approval information.
Action buttons for downloading and sharing the PDF certificate are
provided at the bottom of the screen.

7.1.10 Staff/HOD Dashboard
The staff and HOD dashboard displays pending requests (for staff) or
staff-approved requests (for HOD) in a tabbed interface. Each request
can be expanded to view details and approve/reject with optional remarks.

7.1.11 Admin Dashboard
The admin dashboard provides staff/HOD registration functionality with
fields for name, department, staff ID, password, and role selection.
Bottom navigation provides quick access to data clearing and logout
functions.

7.3 ADVANTAGES

The College Certificate and Request Management System offers several
significant advantages over the traditional paper-based system:

1. Time Efficiency: The digital workflow reduces certificate processing
   time from 5-7 days to 1-2 days, representing an 80% improvement in
   processing speed.

2. Convenience: Students can submit requests from anywhere at any time
   using their mobile devices, eliminating the need for physical visits
   to college offices.

3. Transparency: Real-time status tracking allows students to monitor
   their requests at every stage, eliminating uncertainty and reducing
   anxiety about request outcomes.

4. Accountability: The approval workflow with remarks creates an audit
   trail, making it clear who approved or rejected each request and why.

5. Environmental Impact: Digital processing eliminates paper consumption
   for forms, routing sheets, and printed certificates, contributing to
   environmental sustainability.

6. Data Organization: All requests are stored in a structured database,
   enabling easy retrieval, reporting, and analysis of historical data.

7. Cost Reduction: Reduced paper consumption, printing costs, and
   administrative time translate to significant cost savings for the
   institution.

8. Scalability: The system can handle increasing numbers of requests
   and users without proportional increases in administrative overhead.

9. Accessibility: The mobile-first design ensures that services are
   accessible to all students who own smartphones, which represents
   the vast majority of the student population.

10. Professional Output: Automated PDF generation produces consistent,
    professional-quality certificates with proper formatting and
    institutional branding.

7.4 LIMITATIONS

Despite its advantages, the system has several limitations that should
be acknowledged:

1. Network Dependency: The system requires internet connectivity for
   most operations. While some data is cached locally, request
   submission and approval require active network connections.

2. Device Requirement: Users must have a smartphone capable of running
   the application. While smartphone penetration is high, some students
   may not have access to compatible devices.

3. Learning Curve: Staff and HOD users who are not comfortable with
   mobile applications may require training and support to use the
   system effectively.

4. No Offline Mode: The system does not support offline request
   submission. Requests created offline cannot be stored locally and
   submitted when connectivity is restored.

5. Limited to Three Request Types: The current implementation supports
   only leave, bonafide, and gatepass requests. Other certificate types
   (transfer certificate, conduct certificate, etc.) are not supported.

6. No Real-Time Notifications: The system does not send push
   notifications when request status changes. Users must manually check
   the status screen for updates.

7. Single Database Instance: The system uses a single database instance
   without replication, creating a single point of failure for data
   storage.

8. No Multi-Language Support: The application is available only in
   English, which may be limiting for users who prefer regional
   languages.

8.1 CONCLUSION

The College Certificate and Request Management System (SEC Flow) has been
successfully designed, developed, and tested as a comprehensive digital
solution for academic administrative processes. The system addresses the
key challenges of the traditional paper-based workflow by providing a
modern, mobile-first platform that digitizes the entire request lifecycle
from submission to certificate generation.

Key Achievements:

1. Multi-Role Platform: The system successfully supports four distinct
   user roles (Student, Staff, HOD, Admin) with appropriate access
   controls and functionality for each role.

2. Complete Workflow Implementation: The two-tier approval workflow
   (Staff -> HOD) has been implemented and tested, accurately reflecting
   the institutional hierarchy and approval process.

3. Cross-Platform Compatibility: The application runs on both Android
   and iOS platforms from a single codebase, maximizing reach while
   minimizing development effort.

4. Automated Certificate Generation: The system generates professional
   PDF certificates automatically upon final approval, eliminating the
   need for manual certificate creation.

5. Secure Authentication: JWT-based authentication provides secure,
   stateless access control with automatic token expiration.

6. Department-Based Isolation: The system ensures that staff and HOD
   users can only access data from their assigned departments,
   maintaining privacy and proper delegation.

7. User-Friendly Interface: The intuitive design requires minimal
   training and is accessible to users with varying levels of technical
   proficiency.

The project demonstrates the practical application of modern software
development technologies (React Native, Expo, Flask, MySQL, JWT) to
solve real-world institutional challenges. The system has been tested
and validated through unit testing, integration testing, and user
acceptance testing, achieving a 91.4% test pass rate.

The development of this system has provided valuable learning experience
in full-stack development, cross-platform mobile application development,
RESTful API design, database management, authentication and authorization,
and software engineering best practices.

The system is ready for pilot deployment in a limited capacity (single
department) and can be scaled institution-wide after addressing the
identified limitations and incorporating user feedback.

8.2 FUTURE ENHANCEMENTS

The following enhancements are proposed for future development:

8.2.1 Immediate Enhancements (Next Phase)

1. Push Notifications: Implement Firebase Cloud Messaging (FCM) to send
   real-time push notifications when request status changes, eliminating
   the need for manual status checking.

2. Offline Support: Implement local database caching using SQLite or
   WatermelonDB to enable offline request viewing and queued submission
   when connectivity is restored.

3. Pagination: Implement server-side pagination for request lists to
   improve performance with large datasets.

4. Search and Filter: Add search and filtering capabilities to request
   lists, enabling users to quickly find specific requests.

5. Input Validation: Add comprehensive server-side input validation
   using Marshmallow or Pydantic to prevent invalid data from entering
   the database.

8.2.2 Medium-Term Enhancements

6. Additional Request Types: Extend the system to support other
   certificate types such as Transfer Certificate, Conduct Certificate,
   Course Completion Certificate, and Fee Receipt.

7. Email Integration: Integrate email services (SendGrid, AWS SES) to
   send email notifications for request submissions, approvals, and
   rejections.

8. Analytics Dashboard: Create an analytics dashboard for administrators
   showing request statistics, processing times, approval rates, and
   department-wise breakdowns.

9. Bulk Operations: Enable bulk approval/rejection of requests for
   staff and HOD users, reducing the time required for processing
   large volumes of requests.

10. QR Code Verification: Generate QR codes on certificates that can
    be scanned to verify authenticity, preventing certificate forgery.

8.2.3 Long-Term Enhancements

11. Multi-Language Support: Implement internationalization (i18n) to
    support multiple languages including Tamil, Hindi, and English.

12. Biometric Authentication: Add fingerprint and face recognition
    login for enhanced security and convenience.

13. Integration with Institutional ERP: Integrate with the institution's
    existing ERP system for seamless data synchronization and unified
    user management.

14. AI-Powered Processing: Implement machine learning models to
    automatically categorize and prioritize requests based on urgency
    and content analysis.

15. Blockchain-Based Certificates: Explore blockchain technology for
    tamper-proof certificate storage and verification, providing
    immutable proof of certificate authenticity.

16. Voice Assistant Integration: Add voice-based request submission
    and status checking for accessibility and convenience.

17. Advanced Reporting: Generate comprehensive reports for institutional
    accreditation, compliance, and decision-making purposes.

18. Mobile Wallet Integration: Enable students to store certificates
    in their mobile wallets (Apple Wallet, Google Pay) for easy access.

The implementation of these enhancements will progressively transform
the system from a functional prototype to a comprehensive, production-
ready platform that serves the complete administrative needs of the
institution.
